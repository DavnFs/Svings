# Supabase

Backend configuration for **svings**, a money tracker. Supabase provides Auth, the
Postgres database, and the PostgREST API the Flutter app talks to directly.

## Layout

```
supabase/
├── config.toml              # Supabase CLI config (start/stop/migration settings)
├── apply_all.sql            # GENERATED — everything below, one paste. Do not edit.
├── migrations/              # Versioned SQL migrations (run in lexicographic order)
│   ├── 20260101000001_init_schema.sql
│   └── 20260101000002_rls_policies.sql
└── seed/                    # Demo data (dummy records for development)
    └── 99_demo_users.sql
```

## Applying it to a project

**Easiest — no CLI, no database password.** Open
`Dashboard → SQL Editor → New query`, paste the whole of `apply_all.sql`, and Run.
It contains the migrations and the seed in dependency order.

**Or with the CLI**, if you want migration history recorded:

```bash
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

`db push` applies `migrations/` only — it does **not** run seeds. Apply
`seed/99_demo_users.sql` separately through the SQL editor.

## Local development

```bash
supabase start          # boots Postgres + GoTrue + PostgREST in Docker
supabase db reset       # drops, re-runs migrations, then re-runs seed/*
supabase stop           # shuts everything down
```

## What is in this database?

See [../docs/DATABASE.md](../docs/DATABASE.md) for the full table-by-table reference.

Three tables, all private to one user:

- **Auth** — `auth.users` (Supabase managed) + `public.profiles` (extended profile,
  auto-created by a trigger on signup)
- **Money tracker** — `public.transactions` (replaced the old `history` table)
- **Email sync** — `public.raw_emails` (fetched notification emails, stored before
  parsing so that a re-sync is idempotent)
- **RLS** — every table is per-user; see `20260101000002_rls_policies.sql`

There are no shared or reference tables, and no academic/campus data — an earlier
revision carried a whole university domain that had nothing to do with this app.

The seed is **not** idempotent: it deletes and recreates these rows, cascading to
their transactions. Only run it against data you are happy to reset.

## Regenerating `apply_all.sql`

It is generated by concatenating the migrations and seeds in dependency order. If
you change a migration or seed, regenerate it rather than editing it — otherwise
the copy silently drifts from the source.
